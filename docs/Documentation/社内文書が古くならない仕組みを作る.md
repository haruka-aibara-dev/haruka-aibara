# 社内文書が古くならない仕組みを作る

「社内文書を AI に読ませれば、聞けば答えが返ってくる」という話はよく出る。ただ、社内文書の多くは古い。古い文書を RAG で引いても、古い答えが返ってくるだけで意味がない。

しかも RAG を通すと、古い手順が出典付きのきれいな文章で返ってくる。人が検索していた頃は更新日や書きぶりで「古そうだ」と疑えたが、その手がかりが消える。**古い文書は、検索よりも RAG のほうが害が大きい。**

なので先に考えるべきは、RAG の作り方ではなく、**古い文書が自動で見つかり、更新される仕組み**のほう。

## なぜ古くなるか

文書が古くなるのは、**実態が変わるときに、文書が一緒に変わらない**から。

- システムの構成を変えた PR に、手順書の修正は入っていない
- ツールを乗り換えたが、旧ツール前提のページはそのまま
- 担当が異動したが、「問い合わせは○○さんへ」は残る

「年に1回見直す」ような定期レビューは、この原因に手を付けていない。見直しの間隔の分だけ必ず古くなり、しかも見直しは後回しにされやすい。**変わったときに直す**仕組みにしない限り、常に最新にはならない。

## 1. 書かずに生成する

いちばん確実なのは、**そもそも手で書かない**こと。生成した文書は古くならない。

| 書いてある内容 | どうするか |
|---|---|
| 構成・パラメータ・リソース一覧 | IaC（Terraform など）・設定ファイル・API から生成する |
| API の仕様 | コードや OpenAPI 定義から生成する |
| 担当者・問い合わせ先 | 人事・グループの情報を参照する。本文に名前を書かない |
| 手順 | 可能ならスクリプトや自動化そのものにする |
| なぜそうしたか・経緯 | 手で書く（ADR など） |

手で書くのは「なぜそうしたか」だけにする。判断の記録は日付付きの記録なので、後から古くなっても「その時点の判断」として正しいまま残る。

## 2. 変更と同じ PR で直す

生成できないが、実態と結びついている文書（運用手順・設計の説明など）は、**実態と同じリポジトリに置き、変更と同じ PR で直す**。

- PR を出したら、AI に「この差分で古くなる文書はどれか」を挙げさせ、修正の差分まで出させる
- レビューで文書の修正も一緒に見る
- 別の Wiki に置くと、この流れに乗らない。Wiki に出したいなら、リポジトリから同期する（このリポジトリの Confluence 同期と同じ形）

古くなるのを後から探すのではなく、**古くなる瞬間に止める**。

## 3. コード外の変更をきっかけに探す

組織変更・ツールの廃止・担当の異動のように、PR を通らない変更もある。これは**変更そのものをきっかけ**にする。

- ツールを廃止したら、そのツール名が出てくる文書を全部探す
- 担当が異動したら、その人の名前が出てくる文書を探し、オーナーを付け替える
- 探した結果は、オーナーに「直すか消すか」を回す

全文検索でもできるが、言い回しの揺れ（「旧ポータル」「ポータル」など）は AI に探させるほうが拾える。

## 4. AI が実態と突き合わせて更新案を出す

1〜3 から漏れたものを拾う網として、定期的に AI に突き合わせをさせる。

- 手順書と、実際の設定・IaC を並べて、手順書が前提にしている構成が今もあるか見させる
- 同じ話題の文書同士を並べて、食い違いを挙げさせる
- ずれがあれば、**指摘ではなく更新案（PR や編集の提案）まで作らせる**。指摘だけだと誰も直さない

AI には実態を読む権限だけを渡し、更新の承認は人（文書のオーナー）がする。

## 5. 手順書は実行して確かめる

手順書が正しいかは、読んでも分からない。**実行して通るか**で確かめる。

- 手順をスクリプトや Playwright などで自動化し、定期的に実行する。壊れたら、手順が古いと分かる
- 自動化した時点で、そのスクリプト自体が手順書になる

## 自動で最新にできないもの

人の頭にしかない情報（暗黙の運用ルール、判断の勘所など）は、突き合わせる実態がないので自動では最新にできない。これは「常に最新」を目指すのをやめ、**古いかもしれないことが見える**状態にする。

- オーナーと最終確認日を文書に出す
- 確認日が一定期間より古いものは、表示や検索結果で注意を付ける
- オーナーが名乗り出ないものは、[いらないページを消せる状態を作る](いらないページを消せる状態を作る.md) の「消してよいか」の定例に流す

## RAG はこの上に載せる

この仕組みがあれば、RAG は「最新だと分かっている文書だけ」を引ける。

- 取り込むのは、生成された文書・同じ PR で直る文書・確認日が新しい文書に絞る
- 答えには出典と最終確認日を出す
- 誤答が出たら、プロンプトではなく元の文書を直す。誤答の報告が、そのまま「古い文書の発見」になる

逆に言えば、この仕組みなしで RAG を入れても、古さが見えにくくなるだけになる。

## まとめ

- 古くなる原因は、実態の変更と文書の変更が別々なこと。定期レビューでは解けない
- 生成できるものは生成し、残りは変更と同じ PR・変更イベントで直す。漏れは AI の突き合わせで拾い、更新案まで出させる
- 自動で最新にできないものは、古さが見えるようにして、確認できないものは消す
- RAG はその上に載せる
