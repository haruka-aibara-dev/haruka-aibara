# 社内文書 RAG の前に文書の鮮度を整える

「社内文書を AI に読ませれば、誰でも聞けば答えが返ってくる」という話はよく出る。ただ、その話は **社内文書の多くが古い** という前提を抜かしたまま進むことが多い。

## RAG は古さを隠す

RAG がやっているのは「質問に近い文書を探して、それを材料に答えさせる」ことだけ。文書が正しいかどうかは見ていない。

人が検索していた頃は、ページの更新日や書きぶりを見て「これ古そうだな」と疑えた。RAG を通すと、その手がかりが消える。古い手順が、出典付きのきれいな文章で返ってくる。**古い文書は、検索よりも RAG のほうが害が大きい。**

そのうえ、古い文書と新しい文書が両方あると、どちらを拾うかは質問の言い回し次第になる。同じことを聞いて日によって答えが変わり、「AI は信用できない」で終わる。本当の原因は文書側にある。

## 「先に整備しよう」では通らない

正論だが、整備は成果が見えにくく、予算も担当もつかない。RAG は「やりたい」と言う人がいて予算もつきやすい。なので、**RAG の案件の中に整備を入れ込む** のが現実的な踏み込み方になる。

## 1. PoC の評価で古さを数字にする

PoC を「それっぽく答えたか」で評価すると、古さの問題は見えないまま本番に進む。

1. 実際に社内で聞かれた質問を 20 件ほど集める（問い合わせチャンネルの過去ログなど）
2. RAG に答えさせ、分かる人に正誤を付けてもらう
3. 誤答の原因を分ける

| 原因 | 直す場所 |
|---|---|
| 検索で正しい文書を拾えなかった | RAG 側（チャンク分割・検索方式） |
| 拾った文書が古かった | 文書側 |
| 文書同士が矛盾していた | 文書側 |
| そもそも文書がなかった | 文書側 |

文書側の原因が大半を占めるなら、「RAG を入れる前に文書を直す必要がある」という話が、意見ではなく結果として出せる。

## 2. 全部入れない。取り込む基準を決める

「共有ドライブを丸ごと」「Confluence のスペースを丸ごと」取り込むと、古い文書も一緒に入る。取り込む側で絞る。

- 取り込むのは **オーナーと最終確認日が付いている文書だけ**
- 最初は 1 つの領域（たとえば社内 IT の問い合わせ）に絞る
- 答えには出典と最終確認日を必ず出す。確認日が古いものは答えの中で注意書きを付ける

「オーナーを付ける」「確認日を入れる」作業が、そのまま整備になる。付けられない文書は取り込まない。オーナーが名乗り出ない文書は、[いらないページを消せる状態を作る](いらないページを消せる状態を作る.md) の「消してよいか」の定例に流す。

## 3. 古さの洗い出しは AI にやらせる

整備の手間でいちばん重いのは「どれが古いか見つける」部分で、ここは AI が得意。

- **文書同士の矛盾を出させる**：同じ話題の文書を並べて、食い違っている箇所を挙げさせる
- **実態とのずれを出させる**：手順書と、IaC（Terraform など）や実際の設定を並べて、手順書が前提にしている構成が今もあるかを見させる
- **出てくる固有名詞で見る**：もう使っていないツール名・サービス名・退職者の名前が出てくる文書は、古い候補

AI が出すのは候補まで。消すか直すかは人が決める。

## 4. 誤答は文書側で直す

運用に入ってから誤答が出たら、プロンプトで吸収せず、**誤答の元になった文書を直すか消す**。プロンプトで「この文書は古いので無視して」と書き足すと、古い文書が残ったまま例外が積み上がる。

誤答の報告ボタンを付けて、報告が来たら出典の文書のオーナーに回す。RAG が「古い文書を見つける仕組み」として働き始めると、整備が一度きりの作業で終わらずに続く。

## まとめ

- RAG は文書の正しさを上げない。古い文書を、疑いにくい形で返すようになる
- 「先に整備を」ではなく、RAG の評価・取り込み基準・運用の中に整備を入れる
- 古さの洗い出しは AI、消す・直す判断は人
